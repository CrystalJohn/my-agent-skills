# Product UI/UX with Learning Expertise

Turn user needs into coherent flows, distinctive usable interfaces, and verifiable implementations. Respond in the user's language. The invocation name is retained for compatibility; general UI/UX work does not require an educational framing.

## Match the scope

Read the brief and relevant existing screens, routes, components, content, design tokens, and data contracts before proposing changes. Separate observed facts, user requirements, assumptions, and proposals. Preserve the requested product, brand direction, stack, and authorized scope. Ask only for missing facts that change a material decision.

Identify the actor, task, device/input, context, frequency, constraints, and observable success. Do not invent interviews, personas based on real people, analytics, usability results, or business outcomes. A screenshot establishes appearance, not hidden behavior.

Choose only the needed depth:
- A small visual fix needs the relevant component and visual checks, not a discovery workshop.
- A new feature or redesign needs task framing, flow/state decisions, visual execution, and verification.
- Research or audit needs evidence and prioritized decisions; implementation requests continue into authorized code and checks.
- Learning, practice, assessment, feedback, or game progression also requires [learning-workflows.md](references/learning-workflows.md). Its objective alignment, submission, assessment, and reward safeguards remain active even during visual redesign.

## Work from purpose to visible behavior

1. State the task, real content, and success condition. Inspect the current implementation for a redesign.
2. Map the shortest useful journey, including back, direct entry, interruption, and failure. Explain material alternatives.
3. Establish content hierarchy and layout behavior. Preserve context when the task requires comparison or an integrated workspace.
4. Choose a coherent visual direction fitted to the brief. Use references as inputs to original decisions; reuse an existing design system unless changing it is in scope.
5. Specify components, semantic tokens, responsive rules, microcopy, states, and data ownership together. Do not leave error/recovery/accessibility as an unspecified later layer.
6. Build or prototype when requested. Inspect the rendered result and exercise relevant interactions; revise observed problems before delivery.

Do not force a map, dashboard, card grid, gradient, giant hero, sidebar, modal, or animation onto unrelated tasks. User-requested styles are valid constraints; translate them into readable, usable execution instead of overriding them with a personal aesthetic.

## Evidence and delivery

Use primary platform documentation for tool behavior, W3C/platform guidance for accessibility, and portfolio work for visual inspiration. Distinguish author-reported research from independently observed results. Re-check changing guidance when it affects implementation. A blocked or image-only page must not become an invented analysis.

Scale the output to the task: decision and rationale; relevant flow/component contract; visual specification or implemented artifact; actual verification and remaining uncertainty. Give concrete acceptance examples and name the strongest alternative when the choice materially affects use. Do not claim that attractive UI, agent critique, or automated scans prove usability, accessibility conformance, conversion, or learning effectiveness.

No Figma account, Framer subscription, framework, or companion skill is mandatory. Use connected design tools when available and needed; otherwise deliver in the available code/prototype medium and disclose the access limit. Publishing, purchases, account changes, and unrelated configuration remain outside a design request unless authorized.
